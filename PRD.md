# Product Requirements Document (PRD)

## 1. Executive Summary
The Crowdsourced Festival Stage Optimizer is a 100% autonomous, ML-integrated event data engine. It serves as a digital music stage where the music is driven purely by live crowd voting. Unlike traditional systems where the backend handles logic, this project utilizes a "Thick Database" architecture: PostgreSQL itself acts as the "DJ," monitoring the crowd's energy and autonomously rewriting the playlist when the vibe drops.

## 2. Goals & Non-Goals
**Goals:**
- Showcase advanced database engineering, specifically 3NF normalization, Two-Phase Locking (2PL), and PL/pgSQL triggers/procedures.
- Implement an autonomous queue-shifting mechanism powered by DB triggers.
- Use Spotify Web API and offline ML (K-Means) to group songs into "vibes."
- Provide a dual-interface frontend for the Audience and the Admin.

**Non-Goals:**
- Creating a seamless audio crossfade DSP engine (audio will simply transition track-to-track).
- Building an overarching complex frontend state manager (the DB does the thinking).
- Training complex neural networks (simple K-Means clustering is sufficient).

## 3. User Personas
1. **The Audience**: Festival-goers listening to the music and voting on the current vibe.
2. **The Admin**: The stage manager overseeing the system's autonomous decisions, with the power to override.
3. **The Grader (Professor)**: The academic reviewer evaluating the system for database integrity, concurrency control, and schema normalization.

## 4. Key Interfaces & Detailed Features

### 4.1 Audience Interface
- **Web Audio Player**: Plays 30-second audio previews of tracks using the Spotify API.
- **Current Track View**: Displays the playing song's title, artist, and album art.
- **Queue View**: A read-only list of the upcoming 5 tracks generated by the database.
- **Real-Time Voting Mechanisms**:
  - Prominent "Love this vibe" (+1) and "Hate this vibe" (-1) buttons.
  - Rate limiting to prevent a single user from spamming votes.

### 4.2 Admin Interface
- **System Monitoring Dashboard**:
  - Live display of the `current_vibe_score`.
  - Vote velocity (votes per minute).
  - Currently active `cluster_id` (vibe name).
- **Audit Logs**: A feed of the autonomous decisions made by the database (e.g., "10:04 PM - Vibe score dropped to -50. Autopilot engaged. Switched from Chill to EDM").
- **Manual Override**: A toggle that sets `manual_override = true` in the DB, pausing the autopilot triggers and allowing the admin to force a vibe shift.

## 5. System Logic & Autopilot

### 5.1 Offline ML Clustering (The Music Source)
- **Data Source**: Spotify Web API.
- **Process**: A Python script fetches track metadata and audio features (acousticness, danceability, energy, tempo). It runs Scikit-learn's K-Means algorithm to group tracks into distinct clusters (vibes).
- **Output**: Generates SQL `INSERT` statements to seed the `Tracks` and `Vibe_Clusters` tables.

### 5.2 Database Autopilot
- **Score Tracking**: `Live_Votes` triggers update the `current_vibe_score` on the `Stages` table.
- **Queue Rewrite**: When the score falls below a set threshold (e.g., -50):
  1. The DB deletes all upcoming (unplayed) tracks in `Live_Queue` for that stage.
  2. The DB selects an adjacent vibe cluster.
  3. The DB inserts 5 random tracks from the new cluster into `Live_Queue`.

### 5.3 Concurrency Safety (2PL)
- Under heavy load (thousands of concurrent votes), simple `UPDATE` statements can suffer from lost updates.
- The system will explicitly use `SELECT ... FOR UPDATE` (Two-Phase Locking) to serialize vote tallying, ensuring every single vote is accurately captured.

## 6. Success Metrics
- **Performance**: Zero lost votes during a high-concurrency simulation test.
- **Autonomy**: Sub-second automated queue rewrites executed purely by PostgreSQL.
- **Academic Standard**: The schema perfectly adheres to 3NF/BCNF requirements, supported by a formal Entity-Relationship model.
